## Summary

1. Phase "complete" is a pure projection (`ProjectView.phase_state` -> `phase_completion`) over events, entities and relations. It is mechanical only. Neither the START Skill's Phase-completion list nor the code evaluates the Phase's own desired state, and no canonical text defines what a `phase_integration_check` Work verifies.
2. No single operation owns the transition into "complete". It can be reached by `work_completed` (START), `work_cancelled` (START), a Work `plan_excluded` (Roadmap; measured) and `phase_resumed` (Roadmap). "complete" is not terminal (hold and cancel are still accepted) and it forbids registering new Works into the Phase.
3. Measured gap that supports BL-003's premise: a Work derived with `before_integration=False` can complete after the Phase's only integration; the Phase then becomes complete and START reports `phase_complete` although no integration observed the final Work set.
4. Authority and pins exclude some implementations (not all): `state.py` must not mention Review (test pin + Skill); a Phase has no completion event to authorize; the frozen P2 contract forbids cross-operation Review preconditions; Consumption is unique per terminal event; F1 forbids inferring the contract mode from Work kind or Project state; 44 references in 19 test files (assertions on the legacy `phase_complete` status; one is a docstring) pin that status.
5. Reuse: the P1 gate, record, store, serialization, containment, committed-reader and hermetic-Git primitives are kind-generic. Each landed kind (planning, Work) wrote its own Candidate / Context / Policy / Evidence / proof code. All Work Candidate machinery (owned result paths, K1/K2, resulting tree, isolated verification) is Work-specific. No existing kind binds a Phase's desired-state text.
6. BL-004: the gate mechanism needs neither classification nor a repair loop (both landed kinds ship a severity-final, HIGH/MID-blocking policy with "repair: none"). But under that policy a blocking finding ends in a dead-end `reconcile required` (Work path), and a started Phase's desired state is immutable, so classification (REQUIREMENT CHANGE routing), a review-initiated repair route and re-review identity decide whether a Phase gate is usable.
7. BL-005: durable infrastructure exists (Review records, Event metadata carrier), but reviewer report text is runtime-only (digests are canonical), there is no Phase-level event to anchor to, and legacy events and Roadmap achievement judgement remain bare.
8. Verdict: PARTIAL (see closing block); eight GPT_REVIEW_REQUIRED questions (R4-Q1 .. R4-Q8).

### 1.5 The mechanical gap, measured

- [CURRENT FACT] `start.py` `_derivation_registration` (L1517-1585): when exactly one integration is unfinished, a derived normal Work gets a `requires_completion` into it only if `before_integration` is true; with `before_integration=False` no edge is registered. When no integration is unfinished, deriving a normal Work without a new integration stops with `reintegration_required`.
- [CURRENT FACT] Probe 1 (scratch Project, local Git): W1 completed; W2 derived "Late" with `before_integration=False` and completed; the Integration Work completed; Late completed through `start(..., "outer")`. Result: START status `phase_complete`, `phase_state` `complete`, `work_completed` order W1, W2, Integration, Late, integration count 1. Immediately after the Integration completed, the Phase read `in_progress` with zero unfinished integrations.
- [INFERENCE] The existing mechanics guarantee that an integration exists, not that an integration observed the final Work set. This is a concrete instance of the BACKLOG premise.
- [CURRENT FACT] The in-Phase repair route that exists today is executor-initiated: `Derive` / `HumanNG` outcomes register fix Works and a re-integration (`start.py` `Derive` L167-173, `HumanNG` L177-182, `_derivation_registration`). It runs before an executor returns `Completed`.
