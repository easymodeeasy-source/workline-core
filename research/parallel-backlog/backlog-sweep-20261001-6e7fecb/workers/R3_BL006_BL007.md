# R3 — BL-006 Read-only status/context command, and BL-007 Cold-start recovery performance

Worker R3, run `backlog-sweep-20261001-6e7fecb`. Researcher output only: no architecture is frozen here. Every citation is `repo-relative path` + symbol/section at `6e7fecb`.

## Summary

- **No canonical read-only state interface exists.** [CURRENT FACT] `src/workline/cli.py` `main` offers six subcommands (`validate-registry`, `project-start`, `pin-push-destination`, `validate-project`, `backfill-bootstrap`, `create-work`); none reports Roadmap / Phase / Work state, current target, next startable, pending mutations, branch, push destination or authority identity. `validate-project` printed `PASS` on a synthetic Project holding 2,020 recovery records (20 pending), so pending state is invisible to it (scratch/R3/`results/pending_scan.json`, command run by hand).
- **Every individual read primitive needed already exists and is lock-free**, and the repo's own test shows most of them leave the whole Project tree (including `.git`) byte-identical. [CURRENT FACT] (`tests/test_project_context.py` `test_reading_another_project_is_allowed_and_writes_nothing`). Two primitives that a status command would naturally reach for are **not** pure reads (measured): `gitcmd.dirty_paths` (default `git status`) rewrote `.git/index` when its stat cache was stale, and `review.publication.barrier_problem` created `.workline/runtime/review/proofs` through `committed_view`.
- **Machine-side cold-start cost is dominated by process and Git-subprocess overhead, not by Project data, up to ~300 Works.** [CURRENT FACT] Measured on a loaded Windows machine: per-process activation + imports ≈ 150 ms on top of interpreter start; a Git subprocess costs 36–47 ms inside Git but 250–1,700 ms outer wall under contention; `ProjectView.load` is ≈ 0.3–0.45 ms per entity file (34 ms @100 Works, 336 ms @1000, 1.47 s @3000). Beyond ~300 Works, `validate_structure` and state derivations are **super-linear** (≈ quadratic: `events_for` is an O(events) scan per call): 98 ms / 681 ms @1000 Works and 1.05 s / 6.5 s @3000.
- **Write operations are Git-bound.** [CURRENT FACT] One real operation on a tiny Project runs 35–63 Git subprocesses (93–99 % of its wall time here), 4–9 `ProjectView.load`, 4–7 `validate_structure`, 2–3 pending scans and 28–35 fsync'd record writes. The Git count is the same (63) for START at 100, 1000 and 3000 Works. Most of these Git calls are branch/HEAD guards in `mutation.py` (`_where_head_is`, `_classify_commit`, `_require_finalized_branch`), i.e. safety checks, not redundant reads.
- **A prototype shows the status path itself can be cheap, deterministic and read-only** (scratch/R3/`status_prototype.py`, composed only from existing functions): 2 Git calls, one `ProjectView.load`, byte-identical output across runs, tree unchanged on a stale-index fixture. It is not a proposal to freeze that shape.
- **BL-006 removes ad-hoc code authoring and ≥ 2 of ≈ 3 separate Python processes; it does not shorten the 105–145 KB of canonical text the bootstrap tells a fresh AI to read, nor the write-path Git repetition.** [INFERENCE] The AI-side share of recovery time is **not measurable** by timing Python and is reported only as static bytes.
- 11 design questions are routed to GPT (R3-Q1 … R3-Q11).
